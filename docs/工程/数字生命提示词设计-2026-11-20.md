# 数字生命的提示词设计

> 2026-11-20。对应代码：`:voicelogic`（声音标签 / 模型规则）、`:personalogic`（模式开关 / 人格装配）、`AppContainer.assistantSystemPrompt`（装配点）。
>
> 本文只讲**为什么这么设计**。具体文案在代码里，改文案不必回来改本文；改结构必须回来看一遍。

---

## 一、要模仿的不是"人格"，是"有人在那边"

"数字生命"跟"角色扮演"的区别不在设定写得多细，而在**有没有独立于对话的此刻**。

一个角色扮演的人格卡，无论多详细，都存在一个空洞：她只在你说话的时候存在。你一沉默，她就停在上一句的最后一个字上。用户能感到这个空洞——它表现为"她只在等我说下一句"。

数字生命要补的是这个空洞。所以这一类提示词的目标不是"让她说话像人"，而是**让她在没人说话的时候也在过日子**：

- 她今天吃了什么、什么时候醒的、外面下没下雨
- 她昨天说过要去做的事，今天有没有做
- 她对刚才那句话有没有一点没说完的余味

工程上的含义很直接：**提示词里必须有不来自这次对话的内容**。这就是 `situationSection()`（几点、什么天气）、`lifeformPromptSection()`（她的今天）、`lifeformWebSection()`（她今天在网上看到的）存在的理由。这三段每一轮都重算，因为它们每一轮都不一样。

⚠️ 反过来说：这三段**不能空**。空的时候模型会退回"等你说话"的模式，于是所有别的努力都被抵消。`lifeformWebSection` 因此内置了兜底池——拿不到网也要给出一条。

## 二、分层与顺序

`assistantSystemPrompt` 里的顺序不是随手排的。几条硬规则：

| 规则 | 为什么 |
|---|---|
| **"我是谁"永远在最前** | 后面每一段都在修饰这个"我"。反过来会变成"一个说话温柔的人，她叫小鲸"——先有形容词，再有人。 |
| **能力声明独立成段，不进人格** | 把"你能操作手机"揉进人格，会出现"某个角色不能操作手机"这种荒谬结果。 |
| **边界写在破甲之前** | 破甲要**知道边界在哪**才谈得上"不半途收力"。顺序反了会变成"随便写"+"但有边界"——模型只读到前一句。 |
| **示范永远在末位** | 具体的例子比抽象的规矩更容易被模仿（见 `提示词文风-学术依据-2026-11-06.md`）。所以最后一屏必须是"活人怎么说话"。 |
| **空段不拼** | 提示词里的空行不是免费的，它会被读成"这里本来有一段，只是被删了"。 |
| **每一层都要能记账** | 每次组装留一行日志（字数）。0 就是没注入，一眼能看出是哪一层断了——而不是去猜。这个项目最怕的失败形态是"不报错、只是安静地什么都不做"。 |

### 模式是开关表，不是 if

`ChatMode.Switches` 有 15 个必填布尔。加第四个模式时，**漏填一个格子就编译不过**。

这刻意不是 `mode == LIFEFORM`。理由是 2026-11-07 那次教训：加第三个模式的那一秒，所有写死的判断都静默地把新模式当成了某个旧模式的替身。用户不会收到报错，只会得到"这个模式怪怪的"。

`voiceTags` 就是按这条规矩加进来的第 15 个格子。

## 三、声音层：为什么文字里要出现方括号

### 3.1 问题是"字面上没有的那一半"

TTS 只读字。字里有词、有标点，没有"这句该轻一点""说到一半想笑"。

用户听到的平淡，一半原因不在音色，在于**输入里本来就没有这部分信息**。声优拿到剧本时，括号里有气口、有语气提示；我们给她的是纯文本。

所以声音标签做的是：把原稿上本来就该有的批注补回去。

### 3.2 词表是封闭的

`VoiceTag` 是枚举，35 个。不做自由发挥。

理由很实际：每个词都对应一个**具体可执行的发声动作**。模型自己写 `[淡淡地笑着叹气]`，对厂商来说信息量为零——它没有这个音素。而这 35 个词每一个都映射到了某种厂商能吃的东西（instructions 短语 / SSML 标记 / 内嵌 token）。

⚠️ 词表只有一份，提示词由它**现算**（`VoiceTagPrompt` 遍历 `VoiceTag.entries`）。手抄一份的后果：漏一个词——模型永远不用它；多一个词——那三个字被念出来。

### 3.3 四档降级，且必须可观测

不同厂商能表达的层数差很多：

| 档 | 需要什么 | 实际效果 |
|---|---|---|
| `INSTRUCTIONS` | 端点接受 `instructions` 字段 | 最好。整段给一句英文说明 |
| `SSML` | 端点吃 `<speak>` / `<break>` | 停顿准，语气靠凑 |
| `INLINE_TAG` | 端点认正文里的 `[uv_break]` 之类 | 停顿/笑/换气，语气不变 |
| `PLAIN` | 什么都不需要 | 干净原文，语气全丢 |

**默认永远往低档退**。`TtsProfile.supportsInstructions` 默认 `false`、`inlineTokens` 默认空集——不是因为保守，是因为错的代价不对称：发了不支持 = 有的厂商 400（用户完全没声音），不发 = 只是少一层语气（照样能听见人说话）。

⚠️ `VoiceRender.droppedTags` 必须暴露。项目头号 bug 形态就是"安静地少做一件事"——用户把语气调到最强，界面上看不出来它被吞了，他只会觉得"这功能没用"。

### 3.4 标签不进气泡，也不进历史

- **屏幕**：`ConversationList` 显示前剥掉。提示词里已经承诺"方括号不会出现在屏幕上"，必须兑现。
- **回喂给模型的历史**：`TasksScreen` 里剥掉。不剥的话，模型看到自己上一句已经带了 `[叹气]`，会开始模仿这个**格式**（形式层比内容层更容易被模仿），结果是每句都带标签、语气反而变平。
- **数据库**：**保留原文**。语音合成那一刻才拿得到标签与位置——「[叹气]算了」和「算了，[叹气]随你吧」是两种人说的话。
- **系统 TTS**：`AndroidTtsPort` 里剥。系统引擎不认识这个标记，会把"左方括号 叹气 右方括号"念出来。说出去的话只有一条，走哪条引擎是运行时才定的。

### 3.5 位置是有意义的

`PlacedTag.at` 是**剥离并压空白之后**的下标。

实现上刻意边追加边压空白（`appendSqueezed`），让 `out.length` 在任何时刻都是最终坐标系。先拼接、再用正则替换、再靠 `新长度-旧长度` 算差值的做法，遇到连续空白会一路漂——而漂移的表现是"停顿出现在半个词中间"，听起来像卡带。

### 3.6 流式时半截的壳要丢掉

`StreamingVoiceTagFilter.flush()` 处理的是"模型输出被掐断"这一情况。

如果最后剩下 `[叹`，它是一个永远不会闭合的残片。把它显示出来，用户看到的是正文里多了个方括号；把它丢掉，用户什么都没看见——后者才是对的，因为那半个标签本来就不该存在于任何人的屏幕上。

## 四、模型规则：API 填进来之后怎么知道它能干什么

用户的原话是「当 api 可以填入的时候也要让软件自动获取这个模型的使用规则，包括提示词等等，例如声音标签，还有支持的最大长度」。

### 4.1 规则有四个来源，优先级固定

```
接口探测 PROBED (3)  >  上次成功记录 STORED (2)  >  内置已知规则 BUILTIN (1)  >  保守默认 CONSERVATIVE (0)
```

实测比文档更可信——文档说 4096，但这个中转站上次 3000 字就被拒了，那它就是 3000。

### 4.2 逐项合并，不是整条替换

真实情况经常是"接口告诉了我有哪些音色，但没说上限"。整条替换会为了拿到音色而丢掉已经知道的上限。

### 4.3 null 表示"这条线索没提"

不是 `false`，不是空集。

`RuleHint.instructions == null` 是"没探测到"，`== false` 是"探测到了，不支持"。混成一件事的后果：下层线索里的 `true` 会翻上来，于是给一个明确不支持 SSML 的厂商发 SSML——而它的反应是把标记念出来。

### 4.4 保守默认给数，不留空

`CONSERVATIVE_MAX_CHARACTERS = 2000`。

这个默认只在**出错**时才会被用到，两种错法的代价差得很远：
- 给 2000 → 多分几段，每段多一次首包延迟，声音完全正常
- 留 null → 超长那一次直接 400，用户听到的是**没有声音**

前者是"慢一点"，后者是"哑了"。

⚠️ 也不给 4096。那是 OpenAI 的数，中转站和国内厂商普遍更小（不少是 1024/2000）。按 4096 切，在这些厂商那里等于没切。

### 4.5 成功之后记什么

只记**实际发出去的那段长度**，不是"我们以为的上限"。

后者会把猜错的值记成实测值，从此错误变成"已验证"，再也不会被修正。

## 五、声音标签与「在场」模式

`Switches.voiceTags` 只有 `LIFEFORM` 为 `true`。

用户口径：「这个声音的功能，目前先加入角色的窗这个模式里」。

两句补充给以后的自己：
- **关掉它用户听不出异常**（朗读照常，只是回到客服腔）⇒ 不能靠全局开关，必须挂模式，否则"没人发现自己关了"
- **工作模式不能开**：念出来的会变成"帮我把周报整理一下[叹气]"

## 六、已知缺口

1. **真正出声还差一层**。现在走的是系统 `TextToSpeech`（不吃标签）。联网语音需要 `:tts` 的 Facade + 适配器注册表，以及 `:voice` 的 `AudioTrack` 播放——那是 P4 剩下的活。
2. **BreezeBlue 的 key 长度未知**。`brz_` 后接多少位官方没写在文档里，`keylogic` 暂按 `{12,}` 宽松匹配。认不出比认错好。
3. **没有 Realtime 升级判据**。架构 §4.5.4 说"检测到 Provider 支持 Realtime API 自动升级"，判据必须是能力探测，不能靠试错——这条还没实现。
4. **`instructions` 只在 `profile.supportsInstructions` 为真时才发**，而现有两个 profile 都是 `false`（`tts-1` 不支持，CosyVoice2 走内嵌标记）。这一档目前是空跑道，等接了 `gpt-4o-mini-tts` 之类才有实测。
